# Step-by-Step Portfolio Guide

Build and understand the projects in this order. Each stage produces evidence you can show in GitHub and discuss in an interview.

## Prepare your tools

Install Python 3.11 or newer, Git, and a code editor. Download and extract this repository; open a terminal inside product-analytics-portfolio.

If the repository has already been created for you, use GitHub's Code menu to copy its clone URL or download a ZIP. When cloning, type `git clone ` followed by the copied URL, then run `cd product-analytics-portfolio`. Skip the later repository-creation section and use the existing repository.

```bash
python --version
git --version
```

If Windows recognizes `py` but not `python`, use `py` throughout. No pip install is required for the local version.

## Run all three projects

```bash
python -m demo
```

The demo runs input generation, loading, quality checks, replay verification, metric exports, AI-query checks, and a generated results report. Outputs are saved under data/demo/exports. It is safe to rerun without duplicating accepted events.

For the optional static charts:

```bash
python -m pip install -r requirements-viz.txt
python -m demo --figures
```

Open data/demo/exports/product_analytics.png for the four-panel chart and results.md for the measured synthetic results. Committed sample outputs are also available under docs/evidence.

## Run the event pipeline

```bash
python -m unittest discover -s tests -v
python -m pipeline.generate
python -m pipeline.run
```

Inspect the console output. The pipeline should report passing quality checks, two intentional invalid records, and one intentional replay. The accepted-event count is generated by the program; do not copy a guessed number into your resume.

Read these files in order:

1. docs/EVENT_CONTRACT.md
2. pipeline/generate.py
3. pipeline/run.py
4. tests/test_projects.py
5. docs/RUNBOOK.md

Run the load again:

```bash
python -m pipeline.run
```

Confirm inserted_events is zero. This is evidence of idempotent replay.

The automated tests also check late arrivals, repeatable backfills, event-ID conflicts, malformed input, stale data, duplicate experiment assignments, and model relationships.

### Make one meaningful change

Add a new event type to the contract, generator, validator, and tests. Decide whether it counts toward engagement and explain why. This provides a concrete extension you can explain and validate.

Commit it:

```bash
git init
git add .
git commit -m "Build validated synthetic product event pipeline"
```

If Git asks for your identity, configure your real name and preferred commit email locally. Never use a password or token as a Git identity.

### Create your Tableau dashboard

This workbook is a manual extension, not included in the starter.

1. Open Tableau with a license or product you are authorized to use.
2. Connect to the exported CSV files.
3. Build a DAU line chart: activity_date on columns, daily_active_users on rows.
4. Build an activation trend: signup_date on columns, activation_rate on rows.
5. Build a cohort heatmap: cohort_date on rows, day_offset on columns, retention_rate on color and label.
6. Show the three session funnel counts as separately labeled values or reshape them into a stage/count table before building a bar chart.
7. Use weighted rates when combining cohorts: sum retained_users divided by sum eligible_users. Do not sum percentages.
8. Add captions documenting synthetic data, UTC, exact-day retention, and observation-window limitations.
9. Save the workbook and add screenshots or a packaged workbook only after checking that no private data is embedded.

Keep each metric table's grain intact. Avoid physically joining unrelated daily, cohort, and user-level exports into a single flat table; use separate sources or deliberately defined relationships.

No Tableau account or public publication is required to complete the local SQL project. Publishing a public workbook is a separate decision.

## Create the GitHub repository

You control whether the repository is private or public. Creating a public repository exposes its committed contents, so review them first.

1. Sign in to GitHub.
2. Create a repository named product-analytics-portfolio.
3. Choose Private initially if you want to review before publication.
4. If uploading this existing local Git repository, leave GitHub's automatic README, license, and .gitignore options unselected.
5. Copy the repository remote URL that GitHub provides.
6. In your terminal, type `git remote add origin ` followed by that copied URL.
7. Run:

```bash
git branch -M main
git push -u origin main
```

Use GitHub's supported sign-in mechanism when prompted. Do not paste passwords or tokens into chat or commit them.

After pushing, inspect the repository's Actions tab. The included workflow runs tests and the full synthetic-data workflow. It has been run locally in the supplied sandbox only; the GitHub-hosted run happens after your push.

## Add the original cloud stack

Do this after the local version works. These are implementation milestones, not features already provided.

### Snowflake

1. Use an authorized account and set conservative compute limits.
2. Create a development database/schema and a least-privilege role.
3. Load only the synthetic source records into a raw table.
4. Reimplement validation and immutable event-ID handling with explicit duplicate/conflict behavior.
5. Port the SQLite date functions and JSON expressions to Snowflake SQL.
6. Validate model counts and metric outputs against the local baseline.
7. Keep account credentials out of Git; warehouse usage may incur charges.

### dbt

1. Configure a dbt project against your development warehouse.
2. Create a raw-event source, staging validation layer, dim_users, fact_sessions, and metric models.
3. Add unique, not-null, accepted-value, and relationship tests.
4. Configure source freshness using an ingestion timestamp, while separately monitoring event-time lag.
5. Implement incremental fact loading and document how late data affects dimensions and cohorts.
6. Run dbt build, inspect lineage, and commit only safe project files.

### Airflow

1. Install a compatible Airflow environment using its official version-specific instructions.
2. Create separate generate/ingest, transform, quality-check, and export tasks.
3. Configure dependencies so dashboards refresh only after checks pass.
4. Use a fixed logical data interval so retries and backfills are reproducible.
5. Store connections through the supported secret mechanism, never in DAG code.
6. Demonstrate one failed task, retry, and historical backfill.

Installation commands are deliberately not guessed here: choose a supported Python/tool combination and follow current official documentation when you reach this stage.
